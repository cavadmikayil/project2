{{i:archive-restore}} Giriş: Backup Yalnız Bərpa Olunanda Dəyərlidir

Disk xarab olur, işçi səhvən qovluğu silir, ransomware bütün faylları şifrələyir, server otağını su basır. Bütün bu hallarda yeganə xilas — yoxlanılmış backup. "Backup alırıq" demək kifayət deyil; sual budur: "Nə qədər vaxta, hansı ana qədər bərpa edə bilərik?"

{{i:copy}} 1. 3-2-1 (və 3-2-1-1-0) Qaydası

{{i:copy}} 3 nüsxə

Orijinal + iki backup.

{{i:hard-drive}} 2 fərqli daşıyıcı

Məs. NAS və bulud / lent (tape).

{{i:building}} 1 nüsxə kənarda

Başqa binada və ya şəhərdə (offsite).

{{i:shield-alert}}

Ransomware dövrü üçün əlavə: +1 nüsxə offline və ya immutable (dəyişdirilə bilməyən — məs. S3 Object Lock, WORM) və 0 xəta — bərpa testi problemsiz keçməlidir. Hücumçular əvvəlcə şəbəkədəki backup serverlərini silməyə çalışır.

{{i:layers}} 2. Backup Növləri

NövNəyi kopyalayırBackup sürəti / yeriBərpa
FullHər şeyiYavaş, çox yerƏn sadə — bir set
IncrementalSon istənilən backup-dan bəri dəyişənləriƏn sürətli, ən az yerFull + bütün incremental-lar ardıcıl lazımdır
DifferentialSon full-dan bəri dəyişənləriGünbəgün böyüyürFull + sonuncu differential
SnapshotStorage/VM səviyyəsində an görüntüsüAniSürətli, amma eyni storage-da — tək başına backup deyil

Tipik cədvəl: bazar günü full, iş günləri incremental; 30 günlük gündəlik, 12 aylıq aylıq nüsxə saxlanılır (retention siyasəti, GFS — Grandfather-Father-Son).

{{i:timer}} 3. RPO və RTO

  son backup              QƏZA                 xidmət bərpa olundu
      │◄────── RPO ───────►│◄──────── RTO ────────►│
      │  (itən məlumat)     │   (dayanma müddəti)   │
──────┴─────────────────────┴───────────────────────┴──────► vaxt

{{i:database}} RPO — Recovery Point Objective

Nə qədər məlumat itkisinə dözə bilərik? Gündəlik backup = RPO 24 saat. Bank üçün bu qəbuledilməzdir — replikasiya lazımdır.

{{i:clock}} RTO — Recovery Time Objective

Xidmət nə qədər vaxta bərpa olunmalıdır? 4 saat? 15 dəqiqə? Kiçik RTO bahalı həll (ehtiyat sayt, HA) tələb edir.

{{i:wrench}} 4. Praktiki Alətlər

# /srv/data qovluğunu NAS-a sinxronlaşdır (yalnız dəyişənlər ötürülür)
rsync -aAXv --delete /srv/data/ backup@nas01:/backups/app01/data/

# Əvvəlcə nə edəcəyini göstər (heç nə dəyişmədən)
rsync -aAXv --delete --dry-run /srv/data/ backup@nas01:/backups/app01/data/

--delete mənbədə silinən faylı hədəfdə də silir — yəni rsync güzgüdür, tarixçə saxlamır. Tarixçə üçün snapshot-lu backup aləti lazımdır.

restic -r sftp:backup@nas01:/restic/app01 init        # şifrəli repo yarat
restic -r sftp:backup@nas01:/restic/app01 backup /srv/data /etc
restic -r sftp:backup@nas01:/restic/app01 snapshots
restic -r sftp:backup@nas01:/restic/app01 forget --keep-daily 30 --keep-monthly 12 --prune
restic -r sftp:backup@nas01:/restic/app01 restore latest --target /tmp/restore-test

restic deduplikasiya edir, məlumatı şifrələyir və hər backup ayrıca snapshot kimi saxlanılır. Windows mühitində analoqlar: Veeam, Windows Server Backup.

# PostgreSQL
pg_dump -U app -Fc app > /backups/app-$(date +%F).dump
pg_restore -U app -d app_test /backups/app-2026-09-27.dump

# MySQL / MariaDB (tranzaksiyaları kilidləmədən)
mysqldump --single-transaction -u root -p shop > /backups/shop-$(date +%F).sql

İşləyən verilənlər bazasının fayllarını sadəcə kopyalamaq ziddiyyətli (bərpa olunmayan) backup verə bilər — bazanın öz dump/backup alətindən istifadə edin.

{{i:list-checks}} 5. Bərpa Testi və DR Planı

  1. Hər ay təsadüfi faylı və hər rüb tam serveri test mühitinə bərpa edin.

  2. Bərpa müddətini ölçün və RTO ilə müqayisə edin.

  3. Backup job-larının uğursuzluğu barədə avtomatik bildiriş qurun — səssiz uğursuz backup ən təhlükəlisidir.

  4. DR planı yazın: kim, nəyi, hansı ardıcıllıqla bərpa edir; əlaqə siyahısı, parolların harada saxlandığı, prioritet sistemlər.

{{i:lightbulb}}

Backup-ın şifrələmə açarını və DR planını yalnız bərpa olunacaq serverdə saxlamayın — qəza zamanı ona çatmaq mümkün olmayacaq.
