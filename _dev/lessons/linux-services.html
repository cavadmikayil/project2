{{i:settings}} Giriş: Xidmətlər Necə İşləyir?

Nginx, MySQL, SSH kimi proqramlar arxa planda xidmət (service/daemon) kimi işləyir. Müasir Linux-da onları systemd idarə edir: yükləmədə başladır, çökəndə yenidən qaldırır və log-larını toplayır.

{{i:power}} 1. systemctl ilə Xidmət İdarəetməsi

systemctl status nginx          # vəziyyət, PID, son log sətirləri
sudo systemctl start nginx      # başlat
sudo systemctl stop nginx       # dayandır
sudo systemctl restart nginx    # yenidən başlat
sudo systemctl reload nginx     # konfiqurasiyanı bağlantıları kəsmədən yenilə
sudo systemctl enable --now nginx   # yükləmədə avtomatik başlasın + indi başlat
systemctl list-units --type=service --state=failed   # çökmüş xidmətlər

Öz proqramınızı xidmətə çevirmək üçün unit faylı yazılır:

# /etc/systemd/system/myapp.service
[Unit]
Description=My Python App
After=network-online.target

[Service]
User=myapp
WorkingDirectory=/srv/myapp
ExecStart=/srv/myapp/venv/bin/python app.py
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

Faylı yaratdıqdan sonra: sudo systemctl daemon-reload və sudo systemctl enable --now myapp. Restart=on-failure proqram çökəndə 5 saniyə sonra onu yenidən başladır; xidmət root deyil, ayrıca myapp istifadəçisi ilə işləyir.

{{i:scroll-text}} 2. Loglar: journalctl və /var/log

journalctl -u nginx               # nginx xidmətinin log-ları
journalctl -u nginx -f            # canlı izlə
journalctl -u nginx --since "1 hour ago"
journalctl -p err -b              # bu yükləmədən bəri yalnız xətalar
journalctl --disk-usage           # jurnalın tutduğu yer
sudo tail -f /var/log/auth.log    # giriş cəhdləri (RHEL-də: /var/log/secure)
{{i:lightbulb}}

Troubleshooting qaydası: xidmət başlamırsa, əvvəl systemctl status, sonra journalctl -u xidmət -n 50. Xətanın 90%-i orada yazılır: səhv konfiqurasiya sətri, məşğul port, icazə problemi.

{{i:alarm-clock}} 3. Planlaşdırılmış Tapşırıqlar: cron

┌──────── dəqiqə (0-59)
│ ┌────── saat (0-23)
│ │ ┌──── ayın günü (1-31)
│ │ │ ┌── ay (1-12)
│ │ │ │ ┌ həftənin günü (0-7, 0 və 7 = Bazar)
│ │ │ │ │
* * * * *  əmr
crontab -e      # öz cron cədvəlini redaktə et
crontab -l      # siyahı

# Hər gecə 02:30-da backup skripti
30 2 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1

# İş günləri hər 15 dəqiqədən bir
*/15 * * * 1-5 /usr/local/bin/check-disk.sh

Çıxışı log faylına yönləndirin (>> ... 2>&1) — əks halda cron xətası izsiz itir. Cron-da PATH qısadır, əmrlərdə tam yol yazın.

{{i:key-round}} 4. SSH Açarı ilə Giriş

Parol əvəzinə açar cütü: gizli açar (private key) sizin kompüterdə qalır, açıq açar (public key) serverə qoyulur. Parol təxmin etmək hücumları mənasız olur.

  1. Öz kompüterinizdə açar yaradın: ssh-keygen -t ed25519 -C "aysel@laptop" — açarı passphrase ilə qoruyun.

  2. Açıq açarı serverə köçürün: ssh-copy-id aysel@10.0.0.10 (o, ~/.ssh/authorized_keys-ə əlavə olunur).

  3. Yoxlayın: ssh aysel@10.0.0.10 parolsuz (yalnız passphrase ilə) açılmalıdır.

  4. Yalnız bundan sonra serverdə parol girişini söndürün (aşağıda).

{{i:shield-check}} 5. SSH və Serverin Qorunması

# /etc/ssh/sshd_config
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
AllowUsers aysel deploy

sudo sshd -t && sudo systemctl reload ssh   # sintaksisi yoxla, sonra tətbiq et

# Firewall (Ubuntu - ufw)
sudo ufw allow OpenSSH
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose

# Brute-force qoruması
sudo apt install fail2ban

sshd -t konfiqurasiyada xəta varsa onu göstərir. Dəyişikliyi tətbiq edərkən mövcud SSH sessiyasını bağlamayın — ikinci terminaldan yeni giriş yoxlayın, yoxsa özünüzü serverdən kənarda qoya bilərsiniz.
