{{i:chart-line}} Giriş: "Sayt Yavaşdır" — Amma Harada?

Monitoring əvvəlcədən bilinən sualları cavablandırır: server işləyirmi, disk dolubmu? Observability isə sistemin çıxışlarına (metrika, log, trace) baxaraq əvvəlcədən düşünülməmiş suallara cavab tapmaq imkanıdır: "niyə yalnız Bakıdakı mobil istifadəçilər üçün ödəniş 8 saniyə çəkir?"

OpenTelemetry — üçünü də vahid standartla toplamaq üçün açıq layihə. Tətbiqə bir dəfə əlavə olunur, məlumat istənilən backend-ə göndərilir.

{{i:gauge}} 2. Nəyi Ölçmək Lazımdır

{{i:timer}} Latency

Cavab müddəti — ortalama yox, p95/p99: istifadəçilərin ən pis 5%-i nə görür?

{{i:activity}} Traffic

Sorğu/saniyə, aktiv sessiyalar, Mbps.

{{i:circle-x}} Errors

5xx cavabların faizi, uğursuz əməliyyatlar.

{{i:gauge}} Saturation

Resursun nə qədər dolu olduğu: CPU, RAM, disk, növbə uzunluğu.

Bunlar Google SRE-nin dörd qızıl siqnalıdır. Serverlər üçün USE (Utilization, Saturation, Errors), servislər üçün RED (Rate, Errors, Duration) metodları da geniş istifadə olunur.

{{i:flame}} 3. Prometheus

Prometheus hədəflərin /metrics endpoint-lərini müəyyən intervalla çəkir (pull) və time-series DB-də saxlayır.

# prometheus.yml
scrape_configs:
  - job_name: node                       # Linux serverlər (node_exporter, port 9100)
    static_configs:
      - targets: ["web01:9100", "web02:9100", "db01:9100"]
  - job_name: snmp                       # şəbəkə cihazları snmp_exporter ilə
    static_configs:
      - targets: ["10.0.0.1"]
    metrics_path: /snmp
    params: { module: [if_mib] }
# PromQL nümunələri
up == 0                                                    # çatılmayan hədəflər
100 - avg by (instance)(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100   # CPU %
node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes * 100 < 10
rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m])   # xəta faizi
histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))       # p95 latency
predict_linear(node_filesystem_avail_bytes[6h], 24*3600) < 0   # disk 24 saata dolacaq

{{i:bell-ring}} 4. Grafana və Alert-lər

{{i:layout-dashboard}}

Grafana: Prometheus, Loki, Zabbix, Elasticsearch, CloudWatch-dan dashboard-lar. Hazır dashboard-lar grafana.com-da (məs. Node Exporter Full).

{{i:send}}

Alertmanager: alert-ləri qruplaşdırır, təkrarları susdurur, Telegram, Slack, email və ya PagerDuty-yə göndərir.

# alerts.yml
groups:
  - name: servers
    rules:
      - alert: DiskAlmostFull
        expr: node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes < 0.10
        for: 10m                          # 10 dəqiqə davam edərsə
        labels: { severity: warning }
        annotations:
          summary: "{{ $labels.instance }}: diskin 10%-dən azı boşdur"
{{i:bell-off}}

Alert fatigue: gündə 200 alert gələndə heç birinə baxılmır. Hər alert hərəkət tələb etməlidir və runbook linki olmalıdır; simptoma (istifadəçi xəta görür) səbəbdən (CPU 80%) çox alert qurun.

{{i:target}} 5. SLI, SLO və Error Budget

TerminMənasıNümunə
SLIÖlçülən göstərici300 ms-dən tez cavablanan sorğuların faizi
SLODaxili hədəf30 gündə SLI ≥ 99.5%
SLAMüştəri ilə müqavilə, cəriməli99.9%, pozulsa kompensasiya
Error budget100% − SLO0.5% = ayda ~3.6 saat "pis" vaxt

Error budget qalıbsa, komanda cəsarətlə yeni funksiyalar çıxarır. Budget bitibsə — yeni release-lər dayanır, diqqət sabitliyə yönəlir. Bu, developer və ops arasındakı "sürət yoxsa sabitlik" mübahisəsini rəqəmlə həll edir.
