{{i:repeat}} Giriş: Hər Commit — Potensial Release

Əl ilə deploy belə görünür: serverə SSH, git pull, "test etdimmi?", servisi restart, dua. CI/CD bu prosesi hər dəfə eyni cür işləyən avtomatik konveyerə (pipeline) çevirir: kod push olunur → yoxlanır → paketlənir → mühitlərə çıxarılır.

{{i:git-merge}} Continuous Integration

Developer-lər gündə dəfələrlə main-ə birləşdirir, hər birləşmə avtomatik build və test olunur.

{{i:package-check}} Continuous Delivery

Hər yaşıl build production-a çıxmağa hazırdır; son düymə insandadır.

{{i:rocket}} Continuous Deployment

Testdən keçən hər dəyişiklik insan müdaxiləsi olmadan production-a gedir.

{{i:circle-check}} 1. CI Nə Yoxlayır

{{i:spell-check}}

Lint və format: flake8, eslint, yamllint, terraform fmt.

{{i:test-tube}}

Unit testlər: ayrı funksiyalar saniyələr içində.

{{i:puzzle}}

İnteqrasiya testləri: tətbiq + DB + API birlikdə.

{{i:shield-check}}

Təhlükəsizlik: SAST, asılılıq zəiflikləri, secret scanning.

{{i:package}}

Build: artefakt (konteyner image, zip, binary) bir dəfə qurulur və bütün mühitlərə eyni artefakt gedir.

{{i:timer}}

Sürətli olmalıdır: 10 dəqiqədən uzun CI-ı insanlar gözləmir və yan keçir.

{{i:lightbulb}}

Bu portalın özü də CI istifadə edir: hər push-da build.py check ikonları, dərs kataloqunu, quiz suallarını və qırıq linkləri yoxlayır. Səhvli dəyişiklik sayta çıxmır.

{{i:copy-check}}

Environment parity: mühitlər mümkün qədər eyni olmalıdır — fərqlər "staging-də işləyirdi" problemi yaradır.

{{i:key-round}}

Konfiqurasiya ayrı: eyni image, fərqli environment variable və secret-lər.

{{i:user-check}}

Approval gate: production-dan əvvəl məsul şəxsin təsdiqi (change management).

{{i:workflow}} 3. Tipik Pipeline

  1. Trigger: push, pull request, tag və ya cədvəl.

  2. Checkout və asılılıqların quraşdırılması (cache ilə).

  3. Lint + unit test — paralel job-lar.

  4. Build — myapp:1.4.0-a1b2c3d image-ı və registry-yə push.

  5. Security scan — image-da kritik CVE varsa pipeline dayanır.

  6. Deploy staging → smoke test (curl /health).

  7. Approval → deploy production → monitorinq; problem varsa avtomatik rollback.

{{i:tag}}

Artefakta commit SHA ilə ad verin — production-da hansı kodun işlədiyi həmişə dəqiq bilinir, rollback isə köhnə teqi yenidən deploy etməkdir.

{{i:wrench}} 5. Alətlər

GitHub-a daxildir, YAML workflow-lar, minlərlə hazır action. Növbəti dərsin mövzusu.

.gitlab-ci.yml, öz runner-lər, on-prem quraşdırma üçün populyar.

Ən köhnə və çevik açıq mənbəli server; Groovy Jenkinsfile, çoxlu plugin.
