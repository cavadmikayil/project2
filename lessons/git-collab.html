Git ilə Komanda İşi: GitHub Flow və Pull Request

DevOps · Git
Giriş GitHub Flow Pull Request Sinxronizasiya Konflikt Qaydalar Portal

Giriş: Beş Nəfər, Bir Kod Bazası

Tək işləyəndə Git sadəcə tarixçədir. Komandada isə əsas sual yaranır: hər kəs eyni fayllarda işləyəndə dəyişikliklər bir-birini necə pozmasın və main həmişə işlək qalsın? Cavab — qısamüddətli branch-lar, Pull Request (GitLab-da Merge Request) və avtomatik yoxlamalardır.

1. GitHub Flow

  1. main həmişə deploy oluna bilən vəziyyətdədir.

  2. Hər iş üçün təsviri adlı branch: feature/guest-wifi, fix/ospf-cost.

  3. Kiçik, məntiqi commit-lər və tez-tez push.

  4. Pull Request açılır — CI testləri işləyir, həmkarlar review edir.

  5. Təsdiqdən sonra main-ə merge, branch silinir, avtomatik deploy.

ModelXülasəKimə uyğundur
GitHub Flowmain + qısa feature branch-larVeb, SaaS, tez-tez deploy
Trunk-basedHamı gündə bir neçə dəfə main-ə birləşdirir, feature flag-larlaYüksək səviyyəli CI/CD komandaları
Git Flowmain, develop, release/*, hotfix/*Versiyalı məhsullar, planlı release-lər

2. Yaxşı Pull Request

Kiçik olsun: 400 sətirdən az — review keyfiyyəti ölçü ilə kəskin düşür.

Təsvir: nə dəyişdi, niyə, necə test olundu, ekran görüntüsü; əlaqəli issue: Closes #42.

CI yaşıl olsun: qırmızı testlə review istəməyin.

Review mədəniyyəti: kodu tənqid edin, insanı yox; "niyə belə?" sualı əmrdən yaxşıdır.

Merge üsuluNəticə
Create a merge commitBütün commit-lər + birləşmə commit-i qalır
Squash and mergePR-ın bütün commit-ləri main-də bir commit olur — təmiz tarixçə
Rebase and mergeCommit-lər main-in üstünə ardıcıl düzülür, merge commit yoxdur

3. Remote ilə Sinxronizasiya

git fetch origin                 # yenilikləri yüklə, heç nəyi dəyişmə
git status                       # "Your branch is behind 'origin/main' by 3 commits"
git pull                         # fetch + merge (və ya config ilə rebase)

# Öz branch-ını main-in son vəziyyəti ilə yeniləmək
git switch feature/guest-wifi
git fetch origin
git merge origin/main            # təhlükəsiz: tarixçəni dəyişmir
# və ya
git rebase origin/main           # commit-lərini main-in üstünə köçürür (xətti tarixçə)
git push --force-with-lease      # rebase-dən sonra — yalnız ÖZ branch-ında

git tag -a v1.4.0 -m "Release 1.4.0"   # release-i işarələmək
git push origin v1.4.0

Qızıl qayda: başqalarının istifadə etdiyi branch-da (xüsusən main) rebase və force push etməyin — onların tarixçəsi pozulur.

4. Merge Konfliktini Həll Etmək

İki nəfər eyni faylın eyni sətrini fərqli dəyişəndə Git hansını seçəcəyini bilmir və qərarı sizə buraxır.

$ git merge origin/main
CONFLICT (content): Merge conflict in R1.cfg

$ cat R1.cfg
<<<<<<< HEAD
ntp server 10.0.0.10
=======
ntp server 10.0.0.20
>>>>>>> origin/main

  1. Hər iki versiyanı oxuyun, lazım olsa müəlliflə danışın (git log -p).

  2. Faylı düzgün son vəziyyətə gətirin və <<<, ===, >>> işarələrini silin.

  3. git add R1.cfg → git commit (rebase zamanı: git rebase --continue).

  4. Testləri yenidən işlədin. Vəziyyətdən çıxmaq üçün: git merge --abort.

5. Repo Qaydaları

Branch protection: main-ə birbaşa push qadağandır, PR + ən azı 1 təsdiq + yaşıl CI tələb olunur.

CODEOWNERS: /network/ @netteam — şəbəkə fayllarına dəyişiklik avtomatik şəbəkə komandasına review-a gedir.

Signed commits: SSH və ya GPG imzası ilə müəllifin həqiqiliyi.

Secret scanning və push protection: açar və parol push olunmadan bloklanır.

PR template: .github/pull_request_template.md — hər PR eyni strukturda təsvir olunur.

Semantic versioning: MAJOR.MINOR.PATCH — uyğunsuz dəyişiklik, yeni funksiya, düzəliş.
