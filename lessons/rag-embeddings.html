Embeddings və RAG

AI · Arxitektura
Giriş Embeddings Vector DB RAG axını Chunking Keyfiyyət Ssenari Portal

Giriş: Modelə Öz Sənədlərinizi "Oxutmaq"

LLM şirkətinizin daxili runbook-larını, KB məqalələrini və siyasətlərini bilmir və onun biliyi müəyyən tarixdə dayanıb. Hər şeyi prompt-a yapışdırmaq isə mümkün deyil. RAG (Retrieval-Augmented Generation) həll yoludur: sualla əlaqəli sənəd parçaları əvvəlcə axtarılır, sonra modelə kontekst kimi verilir və model cavabı həmin mənbələrə əsasən yazır.

1. Embeddings: Mənanın Ədədlərlə İfadəsi

Embedding modeli mətni yüzlərlə və ya minlərlə ədəddən ibarət vektora çevirir. Mənaca yaxın mətnlərin vektorları da bir-birinə yaxın olur — hətta eyni sözlər işlənməsə belə.

"Printer çap etmir"          → [0.12, -0.83, 0.44, ...]  ┐ yaxın
"Sənəd növbədə ilişib qalıb"  → [0.10, -0.79, 0.47, ...]  ┘
"OSPF qonşuluğu qurulmur"     → [-0.65, 0.21, -0.08, ...]    uzaq

Keyword axtarış

Dəqiq sözü tapır: "0x2142", "CVE-2024-3400", xəta kodu. Sinonimləri görmür.

Semantik axtarış

Mənanı tapır: "wifi qoşulmur" sualına "simsiz şəbəkə problemləri" məqaləsi. Dəqiq kodlarda zəifdir.

Praktikada ikisi birləşdirilir — hybrid search.

2. Vector Database

Milyonlarla vektor arasında ən yaxınlarını millisaniyələrlə tapmaq üçün xüsusi indekslər istifadə olunur. Yaxınlıq adətən cosine similarity ilə ölçülür.

SeçimXüsusiyyət
pgvector (PostgreSQL)Mövcud PostgreSQL-ə əlavə — kiçik/orta layihələr üçün sadə seçim
Chroma, FAISSLokal, prototip və öyrənmə üçün
Qdrant, Weaviate, MilvusAyrıca vector DB serverləri, filtrlər, miqyaslanma
Elasticsearch / OpenSearchKeyword + vector (hybrid) bir yerdə

3. RAG Axını

HAZIRLIQ (bir dəfə və yenilənəndə)
Sənədlər → parçalara bölmə (chunking) → embedding → vector DB (+ mənbə, tarix, icazə)

SORĞU ZAMANI
İstifadəçi sualı → embedding → ən yaxın 5 parça (retrieval)
      → prompt: "Yalnız aşağıdakı mənbələrə əsasən cavab ver, mənbəni göstər:
                 [parça 1] [parça 2] ... Sual: ..."
      → LLM → cavab + istinadlar

Aktual məlumat: sənədi yeniləyirsiniz — modeli yenidən öyrətmədən cavab dəyişir.

İstinadlar: cavabın hansı sənəddən gəldiyi göstərilir — yoxlamaq asandır.

İcazələr: axtarış istifadəçinin görə bildiyi sənədlərlə məhdudlaşdırılmalıdır.

4. Chunking — Keyfiyyətin Gizli Açarı

ProblemNəticəHəll
Parça çox böyükdürLazımsız məlumat, kontekst israfı, dəqiqlik düşürTəxminən 200–800 token
Parça çox kiçikdirKontekst itir ("bu əmr" — hansı əmr?)Qonşu parçalarla overlap (10–20%)
Mexaniki bölməCədvəl və ya kod bloku ortadan kəsilirBaşlıq, bölmə, paraqraf sərhədləri ilə bölmək
Metadata yoxdurKöhnə və yeni versiya qarışırMənbə, tarix, versiya, şöbə sahələri

5. Keyfiyyəti Necə Ölçmək?

  1. Test sualları dəsti: 30–50 real sual və gözlənilən mənbə sənəd.

  2. Retrieval yoxlaması: düzgün sənəd ilk 5 nəticədə varmı? (Yoxdursa — problem LLM-də deyil, axtarışdadır.)

  3. Cavab yoxlaması: cavab mənbəyə sadiqdirmi (faithfulness), sualı tam cavablandırırmı?

  4. "Bilmirəm" testi: mənbədə olmayan sual — model uydurmamalı, "sənədlərdə tapılmadı" deməlidir.

6. Ssenari: Helpdesk Assistenti

Mənbələr

KB məqalələri, həll olunmuş ticket-lər (anonimləşdirilmiş), IT siyasətləri, vendor sənədləri.

İstifadə

Tier 1 mütəxəssisi müraciəti yazır — assistent oxşar həll olunmuş hallar və addımları istinadlarla təklif edir.

Nəzarət

Təklifi mütəxəssis tətbiq edir; yanlış cavablar qeyd olunur və KB düzəldilir.
